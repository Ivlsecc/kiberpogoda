# Задача 2 — риск цепочки поставок как граф

Оценивает, насколько крупный ритейлер уязвим через поставщиков, и ранжирует
зависимости по риску — с учётом не только прямых связей, но и транзитивных
(поставщик поставщика, ДЗО, общий облачный апстрим).

## Идея

Из того же Certificate Transparency, которым в Задаче 1 мерилась поверхность атаки,
читается карта зависимостей: имена вендоров протекают через поддомены — `keycloak.srm2`
(портал поставщиков), `linkmobile` (SMS-шлюз), `selta` (логистическая ДЗО), `gitlab`
(код). `build.py` сверяет эту доказательную базу с реально собранными в Задаче 1 хостами
(`ct_real.json`), так что мост проверяемый, а не декоративный.

Риск считается двумя взглядами на один граф:

- прямой риск — как в плоской таблице поставщиков (только прямое ребро на заказчика);
- системный риск — с учётом всех путей (noisy-OR), включая транзитивные.

Разница между ними и есть то, что граф видит, а таблица нет: скрытые чокпоинты и
концентрации. Вся математика — в `model.py`, на чистом stdlib.

## Запуск

```bash
pip install -r requirements.txt   # networkx/matplotlib — только для PNG; расчёт на stdlib
python src/main.py                # ранжирование + каскад + граф + сверка CT
python src/sensitivity.py         # устойчивость ранжирования (±25%, 2000 прогонов)
python src/build.py               # отдельно — сверка CT-бриджа
python tests/test_model.py        # 10 тестов
```

Если `networkx`/`matplotlib` не стоят — PNG не рисуется, но `graph.dot` и `graph.mmd`
пишутся всегда (DOT открывается в Graphviz/Gephi, Mermaid вставляется в Markdown).

## Результаты (output/)

- `ranking.md` / `ranking.csv` — зависимости: direct_risk, systemic_risk, усиление, fan-out
- `cascade.json` — пути распространения деградации по каждому источнику (с силой пути)
- `graph.png` / `graph.dot` / `graph.mmd` — граф с подсветкой по системному риску
- `bridge.json` — сверка CT-доказательств с реально собранными хостами Задачи 1

## Ограничения

- Всё выведено пассивно (CT) и из типовых категорий отрасли. Имена вендоров за хостами —
  гипотезы; модель строится на категориях, без непроверяемых утверждений о контрагентах.
- `p_incident` — экспертные приоры, не измерения; калибруются по статистике инцидентов
  сегмента. `sensitivity.py` показывает, к каким выводам это (не)критично.
- Граф — экспертная модель; боевой вариант наполняется из реестра поставщиков и CMDB
  (формат входа `dependencies.json` уже под это готов).
